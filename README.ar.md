# FL Daily Edit

[![Python Version](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

يحدّث FL Daily Edit قوائم الفرق في SP Football Life 2026 وeFootball PES 2021 من خلال
تطبيق الانتقالات الواقعية على ملف حفظ `EDIT00000000`.

## التوافق

تستهدف النسخة الأساسية المرفقة **SP Football Life 2026**. وتتطلب ما يلي:

- Football Life 26 Update 2.2
- SmokePatch's National Squads Update

وهي غير متوافقة مع UML أو الإصدارات الأقدم من FL26 أو التثبيتات التي لا تتضمن
تحديث المنتخبات الوطنية. ابدأ مسيرة جديدة في Master League أو Become a Legend
بعد تثبيت ملف الحفظ.

يمثل [الملف الأساسي المرفق](base/EDIT00000000)
[Gondowan's Mid-Summer EDIT](https://www.reddit.com/r/SPFootballLife/comments/1v7z782/release_gondowans_midsummer_edit_file_more_than/)،
بتاريخ 27 يوليو 2026. ويتضمن أكثر من 500 انتقال، إلى جانب تحديثات للتقييمات
والمراكز وأرقام القمصان وعودة اللاعبين من الإعارة والمدربين والتشكيلات وتغييرات
الصعود أو الهبوط. ولا ينشئ لاعبين أو يضيف الأندية الصاعدة من دوريات الدرجة الثالثة.

## مُثبِّت Windows

مُثبِّت Windows هو الخيار الموصى به للمبتدئين. تتوفر واجهة المُثبِّت حاليًا باللغة الإنجليزية فقط. تستهدف التنزيلات المتحقّق منها حاليًا **Football Life 2026 Update 2.2 + SmokePatch's National Squads Update فقط**. يتوفر اكتشاف vanilla eFootball PES 2021، لكن يظل التثبيت معطّلًا حتى نشر قاعدة أساسية متحقّق منها ومطابقة.

1. نزّل [FLDailyEditInstaller.exe](https://github.com/gvoze32/fldailyedit/releases/download/latest/FLDailyEditInstaller.exe).
2. أغلق اللعبة.
3. اختر **Fast** أو **Deep**. وهما خياران منفصلان لنطاق التحديث، ويعرض كل منهما وقت الإنشاء.
4. أكّد مجلد Football Life 2026 المكتشف، أو استخدم **Browse** عند الحاجة.
5. اختر **Download and install**. يتحقق المُثبِّت من التنزيل، وينشئ نسخة احتياطية من ملف الحفظ الحالي، ثم يستبدله ذريًا.

**تحديث ملف حفظ موجود عبر الواجهة الرسومية:** يمكن للمُثبِّت أيضًا تحديث ملف
`EDIT00000000` ذي التخطيط العام الذي يختاره المستخدم، بدلًا من تثبيت إصدار
مُجهّز مسبقًا. اختر **Update my local save**، وحدد موقعًا مكتشفًا أو استخدم
**Browse**، ثم اختر **Fast** أو **Deep** وبعد المراجعة اختر **Apply update**.
يتحقق المعالج من ملف الحفظ قبل تعديله، وينشئ نسخة احتياطية في مكانه، ويعرض
التقدم والنتيجة أو تفاصيل التشخيص. لا تعتمد أهلية التحديث المحلي على تسمية
SPFL/PES/UML، ولا ينزّل هذا المسار إصدارًا بعيدًا مُجهّزًا مسبقًا.


> [!WARNING]
> الملف التنفيذي الأولي غير موقّع، لذلك قد يعرض Windows SmartScreen تحذيرًا. قبل المتابعة، قارن الملف المنزّل بملف `FLDailyEditInstaller.exe.sha256` المنشور في [أحدث إصدار](https://github.com/gvoze32/fldailyedit/releases/tag/latest).

للتثبيت اليدوي من دون المُثبِّت، نزّل [ملف ZIP لإصدار Fast](https://github.com/gvoze32/fldailyedit/releases/download/latest/fldailyedit-fl2026-fast.zip) أو [ملف ZIP لإصدار Deep](https://github.com/gvoze32/fldailyedit/releases/download/latest/fldailyedit-fl2026-deep.zip) العام. استخرج `EDIT00000000`، وأنشئ نسخة احتياطية من ملف الحفظ الحالي، ثم انسخ الملف المستخرج إلى:

`Documents\KONAMI\eFootball PES 2021 SEASON UPDATE\2026\save\`

للتشغيل عند الطلب أو لاستخدام قائمة أندية مخصصة، أنشئ نسخة متفرعة من المستودع واستخدم **Run workflow** من علامة التبويب Actions.

## ما الذي يتم تحديثه

- الانتقالات والاستغناء عن اللاعبين والإعارات والعودة من الإعارة
- أرقام القمصان المتاحة بالاعتماد على بيانات قوائم الفرق من FotMob
- هويات اللاعبين بعد التحقق منها مقابل قائمة FL26 الحالية
- التشكيلات وخطط اللعب المتأثرة بتغييرات قوائم الفرق
- تقارير الانتقالات وسجلات التدقيق بتنسيق JSON Lines
- ملفات حفظ جاهزة يوميًا عبر GitHub Actions
- إنشاءات اللاعبين المصادق عليها وتصحيحات السمات عبر أوامر Player Update الصريحة

لا تستبدل أداة التحديث رقم قميص يستخدمه بالفعل عضو آخر في الفريق. كما تتحقق
من نادي اللاعب الحالي قبل تطبيق أي انتقال.

## خارطة الطريق / مكتملة حاليًا

اكتملت جميع عناصر خارطة الطريق الحالية. ننتظر الفكرة المفيدة التالية.

## الأمان والقيود

- تنشئ عمليات التشغيل المحلية نسخًا احتياطية متعاقبة، وتستخدم تشفيرًا ذريًا تم التحقق منه.
- يجري التحقق من ملفات الحفظ قبل تغييرات قوائم الفرق وبعدها.
- يمنع قفل العملية تشغيل عمليتين تكتبان إلى المخرَج نفسه في الوقت ذاته.
- تؤدي لقطات FotMob غير المكتملة إلى إيقاف التشغيل بدلًا من إنشاء ملف حفظ جزئي.
- يجري تخطي مطابقات اللاعبين الملتبسة، وحالات عدم تطابق النادي المصدر، والفرق
  التي اكتملت قوائمها.
- تمثل Wikipedia وSortitoutsi وTransfermarkt مصادر تكميلية. ولا يؤدي تعطل أحد
  هذه المصادر إلى إبطال لقطة FotMob مكتملة.
- يتوقف الخيار `--allow-overflow-release` بأمان عند التعذر، لأن الفهرس المرفق لا
  يحتوي على بيانات كاملة للمراكز وOVR لكل لاعب.

## التشغيل محليًا

يدعم الإعداد المحلي macOS وLinux وWindows من خلال WSL. ويلزم Python 3.10
أو إصدار أحدث.

```bash
git clone https://github.com/gvoze32/fldailyedit.git
cd fldailyedit

python3 -m venv .venv
source .venv/bin/activate
pip install -e .

cd vendor/pesXdecrypter
make
cd ../..
```

## الأوامر الشائعة

```bash
# Preview changes without writing a save
python run.py run --dry-run --edit-file base/EDIT00000000

# Validate an existing save
python run.py validate --edit-file base/EDIT00000000

# Validate one-file-per-player updates against the pristine base revision
python run.py players validate

# Apply reviewed Player Updates explicitly to an existing output save
python run.py players apply \
  --base-revision fl26-u2.2-national-squads \
  --edit-file output/EDIT00000000 \
  --in-place

# Apply all effective transfers available through today
python run.py run --window auto

# Rebuild from the bundled base
python run.py run --from-base --window auto

# Update a specific save in place
python run.py run --edit-file /path/to/EDIT00000000 --in-place

# Show every run option
python run.py run --help
```

| الأمر | الغرض |
|---|---|
| `run` | تطبيق الانتقالات التي تم التحقق منها فقط |
| `players validate` | التحقق من جميع تحديثات اللاعبين مقابل النسخة الأساسية الأصلية |
| `players apply` | تطبيق تحديثات اللاعبين التي خضعت للمراجعة صراحةً على ملف حفظ واحد |
| `log` | عرض الانتقالات المطبقة مؤخرًا |
| `inspect` | فحص الفرق وأعداد اللاعبين ومواضع الإزاحة في ملف الحفظ |
| `validate` | التحقق من تسجيلات قوائم الفرق وعمليات ربط خطط اللعب |
| `repair` | إصلاح نسخة أساسية قديمة باستخدام ملفات حفظ مرجعية |

يتعامل `run` مع الانتقالات فقط، ولا يحمّل تحديثات اللاعبين أو يطبقها مطلقًا. وللجمع
بين مساري العمل، شغّل أولًا أمر الانتقالات على ملف حفظ للمخرجات، ثم شغّل
`players apply --in-place` على ملف الحفظ نفسه.

## تحديثات اللاعبين

يمثل كل تحديث لاعب خضع للمراجعة ملفًا واحدًا بصيغة JSON مكتملًا بالإصدار 2 من المخطط لكل
لاعب داخل `players/`. ويسجل `operation` (`create` أو `update`)، ودورة حياة
(`active` أو `upstreamed` أو `retired`)، وإصدارات `applies_to` الأساسية الدقيقة،
وهوية لاعب ثابتة وتوثيق أصل UUID/الملف التعريفي من Pes Retro Stats، والأدلة
المستشهد بها، وبيانات PES التي خضعت للمراجعة. تحتوي تحديثات الإنشاء على سجل لاعب كامل
مقترح وبيانات قائمة الفريق الوجهة. أما تحديثات اللاعبين الموجودين فتحتوي فقط على
القيم المدعومة التي تختلف عن النسخة الأساسية التي تم التحقق منها؛ ويسجل كل تغيير
قيمتي `from` و`to` حرفيًا.
وتشمل مجموعات التحديث المدعومة القدرات وإتقان المراكز وأسلوب اللعب ومهارات اللاعب
وأنماط COM والجنسية والإعدادات البدنية/الأساسية والمركز المسجل.

### المسار المبسط عبر البلاغ

1. افتح [نموذج بلاغ تحديث اللاعب](.github/ISSUE_TEMPLATE/player-update.yml).
   أدخل `Player name` تمامًا كما يظهر في `Pes Retro Stats profile` معتمد واحد،
   وقدّم عناوين URL التي تثبت ذلك، وانتظر حتى يطبق أحد المشرفين التصنيف الدقيق
   `generate-player-draft`.
2. يجلب سير عمل المُنشئ المُهيّأ ذلك الملف التعريفي ويفتح مسودة PR تحتوي على مقترح
   `players/<player-slug>.json` واحد وفق schema-version-2. ويستمد لقطة المصدر
   والهوية والإعدادات البدنية وبيانات المراكز والقدرات وأسلوب اللعب والمهارات وأنماط
   COM من الملف التعريفي.
3. في حالة الإنشاء، لا تبقى مدرجة في `draft.missing` سوى القيم المحلية للعبة غير
   المتاحة من المصدر: معرّفات PES والأسماء المطبوعة للهوية واللاعب، ومعرّف الفريق
   واسمه، ومعرّف الجنسية، ولون البشرة، ولون القزحية. ويجب على مساهم أو مشرف
   تقديمها. أما في حالة التحديث، فيحدد المنشئ اللاعب في النسخة الأساسية التي تم
   التحقق منها، ولا يصدر سوى فروق `from`/`to` الفعلية. ويُحذف مركز مصدر لا يدعمه
   PES 2021، مثل `RWB`، بدلًا من إعادة تعيينه، بما في ذلك حذفه من تغيير المركز المسجل.
4. يراجع مساهم ومشرف كل قيمة منشأة باعتبارها مقترحًا غير معتمد. ولا يقبل CI تحديث
   لاعب إلا عندما يضيف PR مسار JSON معياريًا واحدًا للاعب أو يعدّله بالضبط، وينجح
   المدقق الدلالي المشترك.
5. يظل دمج PR هو حالة الموافقة البشرية. ولا توجد علامة `approved` منفصلة في ملف JSON.

من المتوقع أن يفشل كل مقترح منشأ في التحقق المخصص للملف المكتمل. ولتحويل أدلته
المنشأة إلى مخطط مكتمل بالإصدار 2، أزل الحقول الخاصة بالمسودة فقط
`evidence.current_team` و`evidence.issue_number` و`evidence.issue_url`؛ واحتفظ
بـ`evidence.profile_url` المعتمد و`evidence.proof_urls` التي خضعت للمراجعة
و`evidence.effective_date`؛ وأضف `evidence.reason` غير فارغ بعد مراجعته. احفظ
UUID المعتمد للملف التعريفي في `identity.pes_retro_stats_id`، ولا تضع في `pes`
سوى قيم اللعب التي خضعت للمراجعة. وفي حالة الإنشاء، أكمل أيضًا كل حقل محلي
للعبة مذكور في `draft.missing`. ثم أزل الكائنين `source` و`draft` من المستوى
الأعلى؛ فهما بيانات وصفية لمسودة منشأة مخصصة للمراجعة فقط، وذلك قبل التحقق المكتمل.

### المسار المباشر لطلب سحب بملف واحد

يمكن لمساهم متقدم تخطي المسودة المنشأة عبر البلاغ وفتح PR مباشرةً يضيف أو يعدّل ملف
`players/<player-slug>.json` واحدًا مكتملًا بالضبط. قدّم توثيق أصل UUID/الملف
التعريفي المعتمد في `identity` و`evidence`، والأدلة المستشهد بها، وقيم PES التي خضعت
للمراجعة، وخطوط الأساس المتوقعة للتحديث، ودورة الحياة، وإصدار النسخة الأساسية
الدقيق، ثم شغّل `python run.py players validate` قبل طلب المراجعة. لا تدرج بيانات
`source` أو `draft` الوصفية ذات المستوى الأعلى الخاصة بالمسودة المنشأة. وأبقِ أي
تغييرات أخرى في الشفرة أو الوثائق خارج ذلك PR.

يتم التطبيق دائمًا بأمر صريح ويتطلب الإصدار الدقيق الوارد في
`data/base_manifest.json`؛ ويؤدي عدم تطابق الإصدار إلى الفشل قبل فك تشفير ملف
الحفظ المستهدف.

### دورة حياة المراجعة

عندما تتغير النسخة الأساسية الرسمية، حدّث `base/EDIT00000000` و
`data/base_manifest.json` معًا. احتفظ بتحديثات اللاعبين التاريخية في `players/`؛
ولا تحذفها لمجرد تغير الإصدار. يكون تحديث اللاعب النشط الذي لا تتضمن قائمة
`applies_to` الخاصة به الإصدار الجديد غير نشط: فيبلغ التحقق عن `needs_review`
ويتخطاه التطبيق. وبعد المراجعة، أضف الإصدار الجديد فقط عندما يظل تحديث اللاعب
ساريًا، أو عيّنه `upstreamed` عندما تتضمن النسخة الأساسية الرسمية تغييره، أو عيّنه
`retired` عندما لا يعود ساريًا.

خيارات `run` الشائعة:

| الخيار | الغرض |
|---|---|
| `--deep` | جلب كل نادٍ مفهرس محليًا في FotMob |
| `--club "Chelsea,Arsenal"` | قصر التشغيل على الأندية المحددة |
| `--window auto` | إعادة تشغيل جميع الانتقالات المؤرخة المتاحة حتى اليوم |
| `--window summer` | استخدام أحدث فترة من 1 يونيو إلى 30 سبتمبر |
| `--window winter` | استخدام فترة يناير وفبراير من السنة المحددة |
| `--since YYYY-MM-DD` | تعيين حد أدنى يدوي للتاريخ |
| `--dry-run` | تخطيط التغييرات دون كتابة ملف حفظ |
| `--from-base` | البدء من `base/EDIT00000000` |
| `--fotmob-only` | التشغيل دون مصادر انتقالات تكميلية |

من دون `--from-base`، يستمر التشغيل العادي من آخر مخرَج تم التحقق منه. ويمنع ذلك
اختفاء الانتقالات عندما تقرأ عملية تشغيل مجدولة لاحقة السجل التراكمي مرة أخرى.

## مصادر الانتقالات

يوفر FotMob سجل الانتقالات الأساسي والبيانات الوصفية لقوائم الفرق. وتكمل القوائم
الموسمية في Wikipedia وطلبات الانتقال المفعلة في SortitoutSI وسجلات Transfermarkt
المؤرخة التي تم التحقق منها مسارات الانتقال أو تؤكدها. وتوفر الملفات التعريفية في
Pes Retro Stats مقترحات مستمدة من المصدر وغير معتمدة لمسودات تحديثات اللاعبين.

تجري تسوية السجلات الواردة من مصادر مختلفة دون إسقاط تواريخها أو معرّفاتها أو
استشهاداتها أو روابط إثباتها. ولا يمكن للأحداث غير المؤرخة أو التي سيبدأ سريانها
مستقبلًا أو المتعارضة أو الملتبسة أن تحدّث ملف الحفظ بمفردها.

تبدأ مطابقة اللاعب من قائمة الفريق المصدر، وتستخدم قائمة الفريق الوجهة كخيار
احتياطي يضمن ثبات النتيجة عند التكرار. ولا يؤخذ المركز والجنسية والعمر في الاعتبار
إلا عند توفر هذه المعلومات.

## التطوير

شغّل مجموعة الاختبارات باستخدام:

```bash
pytest -v
```
