# FL Daily Edit

[![Python Version](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

> [!WARNING]
> **Известная проблема / В процессе исправления**: Созданный файл сохранения `EDIT00000000` в настоящее время содержит ошибку/поврежден при загрузке в игре (сброс к настройкам по умолчанию). Мы активно работаем над исправлением целостности файла.

FL Daily Edit обновляет составы команд в SP Football Life 2026 и eFootball PES 2021,
применяя реальные трансферы к файлу сохранения `EDIT00000000`.

## Совместимость

Встроенная база предназначена для **SP Football Life 2026**. Для неё требуются:

- Football Life 26 Update 2.2
- SmokePatch's National Squads Update

Она несовместима с UML, более ранними версиями FL26 и установками без
обновления национальных сборных. После установки сохранения начните новую
карьеру в режиме Master League или Become a Legend.

[Встроенная база](base/EDIT00000000) — это
[Gondowan's Mid-Summer EDIT](https://www.reddit.com/r/SPFootballLife/comments/1v7z782/release_gondowans_midsummer_edit_file_more_than/)
от 27 июля 2026 года. Она включает более 500 трансферов, обновлённые рейтинги,
позиции, игровые номера, возвращения из аренды, тренеров, стартовые составы, а
также изменения, связанные с повышением и понижением клубов в классе. Она не
создаёт игроков и не добавляет клубы, поднявшиеся из третьих дивизионов.

## Скачать последнее сохранение

GitHub Actions ежедневно создаёт обновлённое сохранение и отчёты о трансферах.

> [!NOTE]
> Для скачивания артефактов рабочего процесса GitHub требует войти в учётную запись.

1. Откройте последний успешно завершённый запуск
   [Deep Sync](https://github.com/gvoze32/fldailyedit/actions/workflows/sync-deep.yml)
   или [Fast Sync](https://github.com/gvoze32/fldailyedit/actions/workflows/sync-fast.yml).
2. Скачайте `updated-fl-save-and-reports.zip` из раздела **Artifacts**.
3. Извлеките `EDIT00000000`.
4. Создайте резервную копию текущего сохранения, затем скопируйте извлечённый
   файл в соответствующий каталог:

| Игра | Каталог сохранений в Windows |
|---|---|
| SP Football Life 2026 | `Documents\KONAMI\eFootball PES 2021 SEASON UPDATE\2026\save\` |
| eFootball PES 2021 | `Documents\KONAMI\eFootball PES 2021 SEASON UPDATE\<user_id>\save\` |

Чтобы выполнить запуск по запросу или использовать собственный список клубов,
создайте форк репозитория и выберите **Run workflow** на вкладке Actions.

## Что обновляется

- Трансферы, расторжения контрактов, аренды и возвращения из аренды
- Доступные игровые номера на основе данных FotMob о составах
- Идентификационные данные игроков с проверкой по текущему составу FL26
- Стартовые составы и планы игры, затронутые изменениями в составах команд
- Отчёты о трансферах и журналы аудита в формате JSON Lines
- Ежедневно готовые сохранения через GitHub Actions
- Прошедшие проверку создания игроков и исправления характеристик через явные команды Player Update

Средство обновления не перезаписывает игровой номер, который уже использует
другой игрок команды. Перед применением перехода оно также проверяет текущий
клуб игрока.

## План развития / В работе

Эти задачи запланированы и пока не реализованы:

1. **Восстановить целостность выходного файла** — исследовать и устранить повреждение создаваемого сейчас `EDIT00000000`, а затем усилить валидацию и проверки полного цикла, прежде чем считать выходной файл исправленным.
2. **Установщик/загрузчик с графическим интерфейсом для Windows** — предоставить понятный новичкам `.exe`, который проведёт пользователя через загрузку и установку option file с явным выбором режимов **Fast** и **Deep**.
3. **Несколько проверенных баз** — поддержать создание соответствующих option files из отдельных проверенных баз для **SP Football Life 2026**, **vanilla eFootball PES 2021** и **UML** после предоставления и проверки этих файлов баз.

## Безопасность и ограничения

- При локальном запуске создаются ротационные резервные копии и используется
  атомарное шифрование с проверкой.
- Сохранения проверяются до и после изменений в составах.
- Блокировка процесса не позволяет двум запускам одновременно записывать один
  и тот же выходной файл.
- При неполном снимке FotMob выполнение прерывается вместо создания частичного
  сохранения.
- Неоднозначные соответствия игроков, несовпадения исходного клуба и
  заполненные составы принимающих клубов пропускаются.
- Wikipedia, Sortitoutsi и Transfermarkt используются как дополнительные
  источники. Недоступность одного из них не делает полный снимок FotMob
  недействительным.
- `--allow-overflow-release` завершает работу безопасным отказом, поскольку
  встроенный каталог не содержит полных данных о позиции и OVR для каждого
  игрока.

## Локальный запуск

Локальная установка поддерживается в macOS, Linux и Windows через WSL.
Требуется Python 3.10 или новее.

```bash
git clone https://github.com/gvoze32/fldailyedit.git
cd fldailyedit

python3 -m venv .venv
source .venv/bin/activate
pip install -e .

cd vendor/pesXdecrypter
make
cd ../..
```

## Основные команды

```bash
# Preview changes without writing a save
python run.py run --dry-run --edit-file base/EDIT00000000

# Validate an existing save
python run.py validate --edit-file base/EDIT00000000

# Validate one-file-per-player updates against the pristine base revision
python run.py players validate

# Apply reviewed Player Updates explicitly to an existing output save
python run.py players apply \
  --base-revision fl26-u2.2-national-squads \
  --edit-file output/EDIT00000000 \
  --in-place

# Apply all effective transfers available through today
python run.py run --window auto

# Rebuild from the bundled base
python run.py run --from-base --window auto

# Update a specific save in place
python run.py run --edit-file /path/to/EDIT00000000 --in-place

# Show every run option
python run.py run --help
```

| Команда | Назначение |
|---|---|
| `run` | Применить только проверенные трансферы |
| `players validate` | Проверить все Player Update относительно неизменённой базовой ревизии |
| `players apply` | Явно применить прошедшие проверку Player Update к одному сохранению |
| `log` | Показать недавно применённые трансферы |
| `inspect` | Проверить команды, количество игроков и смещения в сохранении |
| `validate` | Проверить регистрацию игроков в составах и привязки планов игры |
| `repair` | Исправить устаревшую базу с помощью эталонных сохранений |


`run` обрабатывает только трансферы: эта команда никогда не загружает и не
применяет Player Update. Чтобы объединить оба процесса, сначала выполните
команду трансферов для выходного сохранения, а затем выполните
`players apply --in-place` для того же сохранения.

## Обновления игроков

Каждое прошедшее проверку Player Update представляет собой один завершённый
JSON-файл версии схемы 2 для одного игрока в каталоге `players/`. В нём
записываются `operation` (`create` или `update`), состояние жизненного цикла
(`active`, `upstreamed` или `retired`), точные базовые ревизии `applies_to`,
стабильная идентификация игрока и происхождение UUID/профиля Pes Retro Stats,
подтверждающие материалы со ссылками и проверенные данные PES. Обновления,
создающие игрока, содержат предлагаемую полную запись игрока и данные состава
принимающего клуба. Обновления существующих игроков содержат только
поддерживаемые значения, отличающиеся от проверенной базы; для каждого
изменения записываются буквальные значения `from` и `to`.
Поддерживаются следующие группы обновлений: способности, владение позициями,
игровой стиль, навыки игрока, стили COM, национальность, физические и базовые
параметры, а также зарегистрированная позиция.

### Простой путь через issue

1. Откройте [форму issue для обновления игрока](.github/ISSUE_TEMPLATE/player-update.yml).
   Введите `Player name` в точности так, как оно указано в одном каноническом
   `Pes Retro Stats profile`, добавьте URL подтверждений и дождитесь, пока
   сопровождающий назначит точную метку `generate-player-draft`.
2. Настроенный рабочий процесс генератора загружает этот профиль и открывает
   черновой PR с одним предложением версии схемы 2 в файле
   `players/<player-slug>.json`. На основе профиля он определяет исходный
   снимок, идентификацию, физические параметры, данные о позициях, способности,
   игровой стиль, навыки и стили COM.
3. При создании игрока в списке `draft.missing` остаются только недоступные
   в источнике локальные игровые значения: идентификаторы PES и имена для
   отображения для идентификационных данных и игрока, идентификатор и название
   команды, идентификатор национальности, цвет кожи и цвет радужной оболочки.
   Их должен указать участник или сопровождающий. При обновлении игрока
   генератор находит игрока в проверенной базе и выводит только фактические
   различия `from`/`to`. Исходная позиция, которую PES 2021 не поддерживает,
   например `RWB`, пропускается, а не преобразуется в другую; это также
   относится к изменению зарегистрированной позиции.
4. Участник и сопровождающий проверяют каждое сгенерированное значение как
   ещё не утверждённое предложение. CI принимает Player Update, только если PR
   добавляет или изменяет ровно один канонический путь к JSON-файлу игрока и
   общая семантическая проверка завершается успешно.
5. Слияние PR остаётся подтверждением утверждения человеком. Отдельного флага
   `approved` в JSON-файле нет.

Ожидается, что каждое сгенерированное предложение не пройдёт проверку
завершённого файла. Чтобы преобразовать сгенерированные подтверждающие данные в
завершённую версию схемы 2, удалите предназначенные только для черновика поля
`evidence.current_team`, `evidence.issue_number` и `evidence.issue_url`;
сохраните каноническое поле `evidence.profile_url`, проверенные поля
`evidence.proof_urls` и `evidence.effective_date`; затем добавьте проверенное
непустое поле `evidence.reason`. Сохраните канонический UUID профиля в
`identity.pes_retro_stats_id`, а в `pes` — только проверенные игровые значения.
При создании игрока также заполните все локальные игровые поля, указанные в
`draft.missing`. Затем перед проверкой завершённого файла удалите объекты
верхнего уровня `source` и `draft`, которые являются метаданными
сгенерированного черновика только для проверки.

### Прямой путь PR с одним файлом

Опытный участник может пропустить созданный из issue черновик и сразу открыть
PR, который добавляет или изменяет ровно один завершённый файл
`players/<player-slug>.json`. Укажите происхождение канонического UUID/профиля
в `identity` и `evidence`, подтверждения со ссылками, проверенные значения PES,
ожидаемые исходные значения обновления, состояние жизненного цикла и точную
базовую ревизию, а затем перед запросом на проверку выполните
`python run.py players validate`. Не включайте метаданные верхнего уровня
`source` и `draft` из сгенерированного черновика. Не добавляйте в этот PR
изменения другого кода или документации.

Применение всегда выполняется явной командой и требует точной ревизии из
`data/base_manifest.json`; при несовпадении ревизии выполнение завершается до
расшифровки целевого сохранения.

### Жизненный цикл ревизии

При изменении официальной базы обновляйте `base/EDIT00000000` и
`data/base_manifest.json` одновременно. Сохраняйте исторические Player Update
в `players/`; не удаляйте их только потому, что изменилась ревизия. Активный
Player Update, список `applies_to` которого не содержит новую ревизию, считается
неактивным: проверка сообщает `needs_review`, а применение пропускает его. После
проверки добавляйте новую ревизию, только если Player Update по-прежнему
применим; укажите `upstreamed`, когда официальная база уже содержит его
изменение, или `retired`, когда он больше не применим.

Основные параметры `run`:

| Параметр | Назначение |
|---|---|
| `--deep` | Получить данные каждого локально проиндексированного клуба FotMob |
| `--club "Chelsea,Arsenal"` | Ограничить запуск выбранными клубами |
| `--window auto` | Повторно применить все датированные трансферы, доступные по сегодняшний день |
| `--window summer` | Использовать последний интервал с 1 июня по 30 сентября |
| `--window winter` | Использовать интервал с января по февраль выбранного года |
| `--since YYYY-MM-DD` | Установить нижнюю границу диапазона дат вручную |
| `--dry-run` | Спланировать изменения без записи сохранения |
| `--from-base` | Начать с `base/EDIT00000000` |
| `--fotmob-only` | Выполнить запуск без дополнительных источников трансферов |

Без `--from-base` обычный запуск продолжает работу с последнего проверенного
выходного файла. Это предотвращает исчезновение трансферов, когда последующий
запланированный запуск снова считывает накопленную историю.

## Источники трансферов

FotMob предоставляет основную историю трансферов и метаданные составов.
Сезонные списки Wikipedia, включённые заявки на трансферы SortitoutSI и
проверенные датированные записи Transfermarkt дополняют или подтверждают
маршруты переходов. Профили Pes Retro Stats предоставляют полученные из
источника, но ещё не утверждённые предложения для черновиков Player Update.

Записи из разных источников согласовываются без удаления их дат,
идентификаторов, ссылок на источники и подтверждения. События без даты, события
с датой вступления в силу в будущем, а также противоречивые или неоднозначные
события не могут самостоятельно обновить сохранение.

Сопоставление игрока начинается с состава исходного клуба, а состав
принимающего клуба используется как идемпотентный резервный вариант. Позиция,
национальность и возраст учитываются только при наличии этих данных.

## Разработка

Запустите набор тестов командой:

```bash
pytest -v
```

Набор охватывает разбор и проверку сохранений, согласование трансферов,
планирование составов, историю аренд, сопоставление игроков, ограничения
составов, формирование отчётов, резервное копирование и блокировку процессов.
